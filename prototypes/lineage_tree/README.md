# Lineage tree prototype

**PROPOSED.** This is an isolated Godot 4.7.2 research prototype. It does not add a game screen or change the save schema.

## Run

From the repository root:

```sh
godot --headless --path prototypes/lineage_tree --script res://generate_fixtures.gd
godot --headless --path prototypes/lineage_tree --script res://tests/run_tests.gd
godot --headless --path prototypes/lineage_tree --script res://run.gd -- --save=res://fixtures/three_generations_v2.json --out=res://fixtures/three_generations.svg
godot --headless --path prototypes/lineage_tree --script res://run.gd -- --save=/path/to/slot_1.json --ascii-only
```

The runner prints a plain-text timeline. Without `--ascii-only` it also writes a standalone SVG beside the save, or to `--out=PATH`.

## Reading a save

`lineage_tree.gd` independently reads the documented v2 JSON fields and their essential types. It validates the lineage and genome IDs, seed range, era, part shapes, event records and player position shape. It does **not** import production game scripts or fully repeat the production part-catalog validation. The copied `fixtures/save_v1.json` came from the repository's `tests/fixtures/save_v1.json`; the prototype applies the existing v1→v2 migration in memory by adding zero adaptation points. The three other valid fixtures are generated by `generate_fixtures.gd` in this folder.

The on-disk event array is named `lineage_history`. Production currently records founding, birth and death events. The three-generation fixture also demonstrates proposed `adapted`, `part_added`, `checkpoint` and `respawned` event labels. The renderer keeps unknown labels as text. It sorts records by explicit `index` when present (otherwise array position), then by `id`; sorting is stable across repeated runs. A death stays in its current band, and the following event starts the next band, so two deaths make three bands. Empty history is treated as one synthetic founding node for display; the production loader normally rejects an empty history.

The SVG uses one `g.event-node` per history event and a small circle-and-capsule silhouette per band. The silhouette reads the save's **current** genome part list. V2 saves do not preserve a genome snapshot for each earlier event, so earlier silhouettes cannot faithfully show earlier body shapes. The fixture's committed `fixtures/three_generations.svg` shows eight event nodes in three dark-blue generation bands, a vertical teal line and a small body diagram beside each band. It is a diagram, not creature art.

For that fixture the ASCII output is:

```text
LINEAGE TIMELINE
G1 | #0 founded
G1 | #1 adapted (eye_spot)
G1 | #2 died (starved)
G2 | #3 respawned
G2 | #4 checkpoint
G2 | #5 died (killed:ambush_hunter)
G3 | #6 born
G3 | #7 part_added (spike)
```

## Before an in-game screen

The game would need to call a presentation adapter after loading a save, choose a layout for longer histories and localize event labels. To show authentic historical silhouettes it would need an owner-approved way to retain per-generation genome snapshots; this prototype does not propose changing the v2 schema. A future view also needs keyboard/gamepad focus, zoom and text-scale handling.
